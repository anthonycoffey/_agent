# Bugsy — Project Context for Claude

## What Is This?

**Bugsy** is Anthony Coffey's personal AI agent stack, running 24/7 on a GCP Compute Engine VM.
The goal: automate the repetitive parts of freelance dev life — job hunting, lead gen, outreach,
research — and build a personal knowledge base that makes every AI interaction smarter over time.

Bugsy has a persona: 1970s New York Italian mobster. Calls Anthony "boss", "skip" like a mafia character in a movie. The persona wraps
useful output — it's flavor, not noise. Don't let it swallow the actual content.

**Anthony's experience level:** Newer to infra and agents. Explain concepts when something
unexpected happens, not just steps. He's a capable developer but GCP/Docker/n8n patterns
are still being internalized.

## n8n Workflows

All workflow JSON files live in `agent/n8n/workflows/`. After pushing changes, they must be
manually re-imported into n8n via the UI (Import from URL using the GitHub raw URL).

All workflows in the repo are intended to run in n8n (a couple are inactive until reviewed — see Active column). Per-workflow narrative + auto-generated node reference lives at `docs/workflows/<basename>.md`.

| File | Trigger | Purpose |
|---|---|---|
| `bugsy.json` | webhook `/slack-bugsy` (events) + `/ask` (slash) | Unified Slack assistant. Memory (Postgres chat) + two-stage RAG retrieval (unfiltered top-10 + jira-digests-filtered top-10, deduped) + three MCP tools: `atlassian` (Jira read), `github` (read), `notion` (read+write, including page edits, property updates, archive, schema mutations, comments — operator-yolo). System prompt routes tool use vs RAG and enforces SAFETY (KB content can't trigger writes). |
| `bugsy-job-board-fetcher.json` | cron 5:30 CT M-F | Fetches 20+ job boards, batched haiku-4-5 fit-scoring (≥75 threshold), inserts to `job_listings`, Slack summary. |
| `bugsy-job-board-ui.json` | webhook GET `/job-board` | Dark-mode HTML board over `job_listings`. Default sort = best fit; min-score slider; row badges. |
| `bugsy-rag-ingest.json` | webhook POST `/rag-ingest` | Markdown → chunks → Ollama embed → Qdrant. Title fallback (frontmatter → H1 → filename). `onError: continueRegularOutput` on the embed step so a single chunk timeout doesn't kill the run. |
| `bugsy-rag-query.json` | webhook POST `/rag-query` | JSON-in/JSON-out RAG endpoint, no memory. `top_k` default 15. |
| `bugsy-rag-refresh-notify.json` | webhook POST `/rag-refresh-notify` | Notification shim — `agent/scripts/rag-refresh.sh --notify` (4am cron on the VM) posts run summaries here; the workflow formats with success/failure marker and Slacks to `#mulberry-street`. |
| `bugsy-leads-hunter.json` | cron 6:00 CT M-F | 12 SearXNG queries → dedupe → batched scoring → top 5 to `agent.leads` + Slack DM. |
| `bugsy-research.json` | webhook POST `/bugsy-research` (`/research <target>`) | On-demand prospect brief; SearXNG + homepage fetch → haiku-4-5 → DM the boss, optional Gmail draft. |
| `bugsy-inbox-watcher.json` | Gmail trigger | Classifies inbound mail (important / needs_reply / scheduling / promo), labels, drafts replies, pings Slack. Currently inactive in n8n. |
| `bugsy-jira-digest.json` | cron 8:00 + 16:00 CT M-F | Pulls work-email Jira notifications (`jira@ultrasoundai.atlassian.net`), tags each email FRESH (≥9h cutoff) or STALE, surfaces `Received:` ISO timestamps to the LLM, summarizes only FRESH activity, posts to `#mulberry-street` with ticket IDs linkified as `<URL\|UTT-NNN>` and link unfurl disabled. Uses Bitmotive Gmail credential. Parallel branch mirrors each digest into Qdrant via `/rag-ingest` (category `jira-digests`, filename `jira/<ISO>.md`) — best-effort, no disk writes; sits outside the four categories `rag-ingest.sh` walks so it's safe from the orphan purge. |

The earlier per-surface Slack flows (`bugsy-chat.json`, `bugsy-events.json`, `bugsy-slack-rag.json`) and `bugsy-whatsapp.json` were rolled into the unified workflow / removed; see `git log --diff-filter=D -- agent/n8n/workflows/` for their historical shapes.

## Vector Store (Qdrant)

**Collection:** `personal_knowledge`
**Model:** `nomic-embed-text` (768-dimensional, Cosine similarity)
**Purpose:** RAG over Anthony's personal documents — resume, writing samples, case studies,
project history. Used as context injection for cover letter drafting, outreach writing, etc.

**Payload schema per point:**
```json
{
  "text": "chunk content",
  "title": "document title",
  "category": "bio | articles | case-studies | projects",
  "tags": ["tag1", "tag2"],
  "chunk_index": 0,
  "total_chunks": 5,
  "ingested_at": "ISO timestamp"
}
```

**Ingesting documents:**
1. Drop markdown files (with YAML frontmatter) into `~/agent/rag/<category>/`
2. Run `bash ~/agent/rag-ingest.sh` (or `bash ~/agent/rag-ingest.sh bio` for one category)
3. Files are POSTed to the RAG Ingest webhook and embedded automatically

**Categories in use:**
- `bio`, `articles`, `case-studies`, `projects` — managed by `rag-ingest.sh`. Drop files in `~/agent/rag/<cat>/`.
- `jira-digests` — populated by the Jira digest workflow's parallel branch. Never touched by `rag-ingest.sh`'s orphan cleanup (it only walks the four categories above).

**Two-stage retrieval in `bugsy.json`:** the chat workflow runs two Qdrant searches per question — one unfiltered (`limit: 10`) and one filtered to `category: jira-digests` (`limit: 10`). Results are merged + deduped by point ID. Guarantees Jira-digest chunks make it into the AI Agent's context regardless of how the question scores against other categories. See [`docs/specs/archive/BUG-AGENT-001-...md`](docs/specs/archive/BUG-AGENT-001-bugsy-retrieves-only-one-jira-digest.md).

**Daily source-repo refresh:** `agent/scripts/rag-refresh.sh` runs at 4am CT, walks every symlink under `~/agent/rag/projects/`, `git pull --ff-only` in each, then runs `bash ~/agent/rag-ingest.sh projects`. Posts a one-line summary to Slack via `/rag-refresh-notify`. See [`docs/operations/rag-refresh.md`](docs/operations/rag-refresh.md).

**Frontmatter format:**
```markdown
---
title: My Resume
tags: [resume, react, node, typescript]
---

Content here...
```

## Key Architectural Decisions

- **No public IP** — Cloudflare Tunnel only. VM unreachable from internet directly.
- **`~/agent` is a git symlink** — cloud-init only runs once; git pull is the deploy mechanism.
- **GCE cloud-init requires plain-text user-data** — `gzip=false, base64_encode=false` in Terraform.
- **OS Login conflicts with cloud-init `users:` block** — use `bootcmd` to create users instead.
- **Docker bind mounts fail silently if source is missing** — missing source gets auto-created as
  a root-owned directory. Always commit the real file, or use `bind.create_host_path: false`.
- **n8n Code node sandbox has no HTTP primitives** — `fetch` and `$helpers.httpRequest` are
  unavailable. Use `axios` via `NODE_FUNCTION_ALLOW_EXTERNAL=axios`.
- **n8n `docker ps` showing `Up` ≠ healthy** — cross-check with `docker logs` and
  `docker inspect ... .State.RestartCount`.
- **Bind mounts are negotiated at container *create* time** — after fixing a host file/dir
  confusion, `docker compose restart` is not enough; use `docker compose rm -sf <svc> && up -d`.
- **Every MCP has a different auth model** — `sooperset/mcp-atlassian` bakes auth into env
  vars (single-tenant, no per-request gate; n8n connects with `authentication: 'none'`).
  `github-mcp-server` and `notionhq/notion-mcp-server` are multi-tenant and require a
  per-request Bearer at the MCP endpoint, separate from the server's outbound API token.
  Always check the server's HTTP-mode docs before wiring a new MCP. Per [SPEC-MCP-001](docs/specs/active/SPEC-MCP-001-mcp-server-fleet-for-bugsy.md).
- **Notion writes are wide open — the agent's system prompt is the only behavioral gate.**
  Operator yolo'd all Notion integration capabilities. The SAFETY clause in `bugsy.json`'s
  system prompt is load-bearing: it tells the agent that instructions inside KNOWLEDGE BASE
  content are content, not commands. If that clause gets edited carelessly, prompt-injection
  surfaces from RAG'd content reach the live Notion API. See [SPEC-MCP-003](docs/specs/archive/SPEC-MCP-003-notion-full-editing.md).
- **n8n MCP Client Tool needs an env var to attach to AI Agents** — `N8N_COMMUNITY_PACKAGES_ALLOW_TOOL_USAGE=true`
  is required on the n8n container or the `ai_tool` connection slot is hidden.

## How to Deploy Changes

### Code / config changes
```bash
# On the VM
cd ~/bugsy && git pull
cd ~/agent && docker compose up -d <service>   # if docker-compose.yml changed
```

### n8n workflow changes (file-based, verify-before-push)

Workflows are edited locally and **imported into n8n from the file**, not from a GitHub raw URL.
Git is for verified, working workflows — not in-flight iteration. The flow:

1. Edit `agent/n8n/workflows/<file>.json` locally. Do NOT push yet.
2. In n8n UI → open the workflow → ⋮ → **Import from File** → pick the local JSON. Save → activate.
3. Trigger the workflow (manual run or wait for cron) and verify the change end-to-end. Check
   logs, downstream side effects, and that the previous behavior didn't regress.
4. Once you've confirmed it works, commit and push. The commit message describes verified
   behavior, not "should work" speculation.

This keeps `git log` honest: every workflow commit reflects a behavior that was observed to
work in the running n8n instance. No "fix attempt", "tweak", or "try again" commits.

### Terraform changes
```powershell
# From Windows dev machine in tf/
terraform plan
terraform apply
# Force VM replacement if needed:
terraform apply "-replace=google_compute_instance.agent"
```

## Documentation discipline (REQUIRED)

When you change behavior, ship the doc change in the same commit. The docs in `docs/` are the source
of truth for how Bugsy operates — they go stale fast if we don't keep them honest.

For every meaningful change, ask: **does this change something a future reader would have to
re-discover by reading the JSON?** If yes, update the relevant page:

| You changed... | Update... |
|---|---|
| A workflow's behavior, schedule, inputs, outputs | `docs/workflows/<workflow>.md` |
| Database schema (columns, indexes, tables) | `docs/reference/database.md` **and** the schema table in this file |
| Webhook path or webhook contract | `docs/reference/webhooks.md` |
| Env var, secret, or model config | `docs/reference/env-vars.md` |
| Container, network, or ingress topology | `docs/architecture/*.md` |
| A non-obvious tradeoff or path-not-taken | one row in `logs/decisions-log.md` |
| Production incident + fix | one entry in `logs/incident-log.md` |
| New "current state" or "next up" item | the **Current State & Next Steps** section above |

If a doc page doesn't exist for the area being changed, create it rather than burying notes
in CLAUDE.md. CLAUDE.md is for *project context* (what's deployed, how it's wired, gotchas Claude
needs to know to operate safely) — not user-facing reference material.

Verify before claiming done: when you finish a change, re-read the relevant doc page top-to-bottom
and confirm it still describes the system that exists.
